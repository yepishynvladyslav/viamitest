# VIAMI NEXT — продуктовый и технический план

**Дата анализа:** 2026-11-09  
**Источник:** 15-страничное ТЗ оригинального VIAMI и проверка приватного репозитория `yepishynvladyslav/Viami` (README, PROJECT-NOTES, firestore.rules, src/ext9.js, src/ext13.js, src/ext14.js, functions/index.js).  
**Важное правило:** оригинальный Firebase project и реальные данные пользователей не использовать для публичной демоверсии.

## 1. Вывод аудита

VIAMI ORIGINAL уже представляет собой функционирующую заготовку группового travel-workspace. VIAMI TEST V2 — только отдельный локальный UX-прототип. **Нельзя считать V2 заменой оригинала.**

Рекомендация: развивать **VIAMI NEXT = оригинальные функциональные возможности + улучшенная навигация/UX + новые модули**, а не переносить оригинальные функции в публичную тестовую копию с нуля.

## 3. Основной пользовательский сценарий (north-star)

1. Пользователь без регистрации читает маршрут или открытое предложение.
2. Создаёт поездку из каталога (клон только публичных маршрутных данных).
3. Приглашает друзей, не теряя анонимный UID.
4. Добавляет скрин/письмо/билет → AI предлагает извлечённые поля; пользователь подтверждает.
5. После подтверждения появляются: бронь в Документах, проверенное событие в маршруте, расход в бюджете, системное сообщение в чате.
6. Участники предлагают правки, голосуют; даты/бюджет фиксируются в версии `TripAgreement`.
7. Начинается день; реальный таймлайн отмечает остановки, предлагает маршрут/ретайм.
8. Возвращение: recap, общий архив, публичная копия маршрута при согласии авторов.

**Продуктовое обещание:** «От скриншота брони и чата с друзьями — к работающему маршруту без переписывания данных».

## 4. Отличающие продукт функции (гипотезы, требуют теста спроса)

### 4.1 VIA Action Cards — не просто AI-чат
AI возвращает структурированное предложение: **Что понял → Что изменится → Предпросмотр → Подтвердить / Отмена**. Никогда не пишет напрямую в БД на основе непроверенного текста.

### 4.2 Booking-to-Everything
Один подтверждённый импорт брони одновременно создаёт 3 согласованные записи (бронь, расходы, событие маршрута) с общим `sourceId`. Повторный импорт не дублирует записи; отмена согласованно отменяет зависимости.

### 4.3 Group Decision Ledger
Предложение даты / жилья / бюджета → голосование → решение → версии условий → подтверждение каждым участником. В чате всегда видно, *какая версия* утверждена. При изменении важных полей — повторное подтверждение.

### 4.4 Open Trips ≠ Route Catalog
Отдельные типы сущностей: `publishedRoute` (повторить маршрут) и `openTripListing` (подать заявку в группу). У публичного предложения: cityFrom, pickupStops, availableCarSeats, destination, tentative dates, budgetBreakdown, min/max, verifiedStatus, join policy, moderation status.

### 4.5 Flight Radar — constraint-aware
Параметры: from airports, destination(s), seasonal interval, adults/children, tripDays/nights, tolerance, luggage, maxTripBudget, noSelfTransfer. Отдельный deterministic duration validator: запрещено предлагать 15 дней вместо 3. Поиск только через разрешённые API (реальная цена + timestamp + deeplink + recheck). Если API нет — честный статус «источник не подключён», **никаких синтетических цен**.

### 4.6 TripPulse
«Что нужно решить сейчас»: неоплаченная бронь, неподтверждённый участник, незафиксированные даты, необходимость купить билеты, несогласованный бюджет. Цель — заменить хаотичные сообщения actionable задачами.

### 4.7 Shareable Trip DNA
После поездки — приватный recap + отдельный публичный маршрут. В публичной версии удаляются личные сообщения, документы, точные места проживания, расходы участников, идентификаторы и приватные фотографии.

## 5. Предлагаемая навигация и дизайн

**Нижняя навигация:** Сегодня · Поездки · Открыть мир · Чат · Профиль.  
**VIA:** контекстная кнопка в разделе и глобальный entrypoint.  
**В поездке:** Мой день (маршрут+карта) · Решения · Документы · Деньги · Медиа.  
**Каталог:** сегмент «Готовые маршруты» / «Ищут попутчиков» — два разных намерения.

Визуально: теплый журнал с Apple-уровнем ясности; крупное hero-фото только на странице места, а не на каждом внутреннем экране. Для discovery — карточки 16:10, крупная цена и доступные места. Для маршрутных задач — компактный таймлайн, чёткая типографика, реальные статусные элементы. Не копировать интерфейсы Apple/Netflix буквально.

Сохранить Onest, существующие 8 тем и светлый/тёмный режим, но выбрать одну дефолтную тему, упорядочить дизайн-токены и компоненты. Проверить safe areas, контраст, фокус, экранную клавиатуру и reduced motion.

## 6. Безопасность — P0 перед публичными открытыми поездками

- В `firestore.rules` текущая декларация `match /trips/{t} { allow get: if signed(); }` разрешает любому авторизованному (включая anonymous) читать верхнеуровневый документ поездки при известном ID. Проверить минимизацию данных и заменить на политики приватности / отдельный public listing.
- `users/{uid} allow get: if signed()` может раскрывать поля профиля; разделить публичную карточку и приватные данные.
- Не копировать исходный Firebase config, пользовательные данные или приватные токены из ORIGINAL в публичный `viamitest`.
- Проверить реальные Firestore Rules через Emulator: чужие поездки, прямая ссылка, revoked invite, spoofed memberIds, emailVerified, авторство, deletion, privilege escalation, nested data.
- KYC только через доверенного провайдера, минимальное хранение; галочка — «ID проверен», не гарантия безопасности.
- Публичные объявления для незнакомых людей: 18+, жалоба, блокировка, support escalation, moderation appeal, Terms.
- AI: server-side quotas per UID, App Check, validation schemas, prompt injection testing, audit log и контроль стоимости.
- `/api/health?k=...` требует review: query token exposure, rate limits, revocation; лучше авторизованный поток с POST и scoped token.
- Нельзя запускать платежи/залоги без юридической проверки marketplace, consumer rights и PSD2/провайдера.

## 7. Миграция инфраструктуры

1. **НЕ менять production Firebase** во время экспериментов.
2. Создать staging Firebase project и приватный staging repository; GH Pages может размещать только публичную сборку без секретов.
3. Snapshot/backup прод-БД и storage перед миграцией.
4. Конвертировать `src/ext*` из глобальных переопределений в ES-модули постепенно с compatibility layer.
5. Вынести изображения `trips/*/blobs` base64 в Cloud Storage, подготовить backward-compatible reader и миграцию, не ломая старые ссылки.
6. Разделить route`days[]` и крупные списки на подколлекции при реальном конфликте записи/нагрузке, сохранить совместимость.
7. Сборка CI: lint, unit, firestore-rules emulator, Playwright, deploy staging → approval → production.
8. Health, location и KYC хранить и распространять исключительно по отдельным политикам согласия, не в общей группе без разрешения.

## 8. Приоритетная поставка

**P0 (reliability):** аудит ACL и XSS, CI и emulator tests, backup, fix duplicate booking, media storage migration, network/offline/error states.  
**P1 (core usability):** один trip workspace, action cards, import preview+undo, group decision ledger.  
**P2 (network):** публичные объявления, фильтры, заявки, status, verification, moderation.  
**P3 (distribution):** flight API integration + alerts, public Trip DNA, recap.  
**P4 (commercial):** правовой/финансовый marketplace анализ, затем платежи.

## 9. Приёмочные критерии флагманской функции

Feature: «Импорт брони → маршрут + документы + расходы».

- При успешном распознавании AI извлечённые атрибуты сначала показываются пользователю, редактируемы.
- Принятие создаёт одну бронь; повтор файла не создаёт дубликат.
- Связанные записи создаются с одинаковым `sourceId`.
- Чек-ин/аут привязаны к корректному дню и часовому поясу.
- Любая ошибка в одном downstream процессе отмечена как частичная и доступна для безопасного повтора.
- Скан-фото, PDF, multiple bookings, валюты, отмены, неизвестные даты и поле с prompt-injection покрыты тестами.
- После перезагрузки данные сохранены; другой участник видит только разрешённые поля.
- Удаление брони предлагает изменить/удалить связанные события и расходы с audit trail.

## 10. UX-исследование и ключевые метрики

Тестировать с 5–10 реальными путешественниками, а не только разработчиком. Сценарии: 1) создать поездку; 2) пригласить 2 друзей; 3) извлечь бронирование; 4) договориться о дате; 5) отметить посещение; 6) поделиться итогом.

Измерять:
- time-to-first-trip
- invite accepted / invite sent
- booking imports with correction / all imports
- % групп, утвердивших дату
- % trip leaders, завершивших поездку с актуальным маршрутом
- 30-day repeat-trip creation
- complaint rate / 100 open trips
- AI API cost / active trip

**Не заявлять**, что гипотезы уникальны или спрос доказан до тестов.
